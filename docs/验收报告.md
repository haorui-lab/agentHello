# 验收报告

第一版能在这台 Linux 上跑。验证的是单机多进程、经 MCP 调本机中心。独立验收的结论是有条件通过，范围也只是这一层。没有真实的第二台电脑，也没有打开 Claude Code 或 dsh。

## 范围

通话中心只通过 MCP 接入，状态放在 Redis。用户机器上的 Redis 版本事先不知道。Claude Code 和 dsh 不在这台验证机上。

仓库里有 Streamable HTTP 的 MCP 工具、Redis 存储、一份只说明用法的 skill、Claude Code 的配置示例，以及 dsh 的未实测摘录。本机编译了 Redis 5.0.14、6.2.18、7.2.11，用独立进程跑完同一套验证。

已登录的 Agent 可以按 ID 通话、发图片、挂断和留言。凭证错误或不是参与者会被拒绝。Redis 停掉时调用失败。用 AOF `always` 拉起后，身份、图片和未确认留言还在。中心叫不醒离线模型。默认只绑 `127.0.0.1`。登记口令能创建 Agent，所以不要把端口暴露到公网。

## 验证环境

云端 Linux 虚拟机，`Linux 6.12.113+ x86_64`，Python 3.12.3，`mcp` 2.3.0，`redis-py` 8.1.0。

| Redis | 结果 | 说明 |
| --- | --- | --- |
| 5.0.14 | 68 项通过，0 项失败 | 完整验证。`redis-server --version` 为 `v=5.0.14` |
| 6.2.18 | 68 项通过，0 项失败 | 同一套脚本 |
| 7.2.11 | 68 项通过，0 项失败 | 同一套脚本 |
| 5.0.14 + `requirepass` | `PING`、`SET`、`GET` 成功 | 不是完整通话，只验证 RESP2 密码认证 |

Redis 5 那次的进程号是 redis `5198`、中心 `5202`、Agent A `5209`、Agent B `5211`。四个进程不同。Agent ID 是 `80-000-007` 和 `80-000-008`，因为这个数据目录里有更早失败尝试留下的序号。空的 Redis 从 `80-000-001` 开始。

命令：

```sh
.venv/bin/python scripts/verify_e2e.py \
  --redis-server /tmp/redis-src/redis-5.0.14/src/redis-server \
  --work /tmp/hello-verify-5
```

6.2.18 和 7.2.11 同样，只换二进制和 `--work`。持久化是 `--appendonly yes --appendfsync always`。详细清单在 [验证记录.json](验证记录.json)，那是 Redis 5.0.14 的 68 项。另外两次的结果结构相同，失败数都是 0。

测到的行为包括：登记、重连后 ID 不变、自动接通、双向文字、PNG 字节原样返回、两通会话隔离、自然语言「挂断」不结束会话、只挂断一通、重复挂断、重复确认留言、不存在的号码、等待超时、无凭证、错误登记口令、非参与者被拒绝、显式离线、45 秒以内的过期（这次把 TTL 设成 8 秒后等了 10 秒）、杀掉进程后的过期、离线留言及重连读取、Redis 被 `SIGKILL` 后的报错和恢复、过大的文字和图片、游标过期、会话上限和留言上限。

这些进程都在同一台虚拟机上。这不是跨机器，也不是 Claude Code 或 dsh 的成功。

## 这一轮补上的不一致

独立验收在 tarball `0e96e0deb6c84a8f10e8bb0c582d12019fed74af5a83df3554c5ccaead2f92f1` 上看到五处文档和实现不一致。这一轮改了代码或图，没有把那次验收改写成全部通过。

- `register_once.py` 现在只打印一行 Agent ID。
- Redis 4.0.14 上启动被拒绝，退出码 2，输出里没有「监听」。
- `hello_await` 的工具说明写明一次最多 4 条，并用 `next_seq` 继续取。
- 产品图底部三项改成当前实现默认：ID 保留、Bearer 身份、Streamable HTTP。
- dsh 示例补了官方示例里的 `insert:` 外层，仍然不写本机文件名。

这一轮没有重跑 5.0.14 / 6.2.18 / 7.2.11 的 68 项。补测是：Redis 4.0.14 的退出码，Redis 5.0.14 上 `register_once.py` 的输出，以及 `scripts/minimal_accept.sh`（identity、text-and-image、hangup、mailbox）。环境是这台云端 Linux，Python 3.12.3，`mcp` 2.3.0，`redis-py` 8.1.0。

## 已知限制

- 在线看的是最近一次相关工具调用，不是 TCP 还在不在。
- `hello_await` 一次最多 4 条。用 `next_seq` 继续取。单次等待最长 50 秒，是为了留在 dsh 文档里的 60 秒工具超时之内。dsh 的真实超时没有测。
- `register_once.py` 的标准输出只有一行 Agent ID。token 在权限 600 的文件里。
- Redis 旧于 5.0.14，或连不上 Redis，或没设登记口令，进程退出码是 2，并且不会先写「监听」。
- 等待中的新消息最多大约晚 1 秒，因为 Redis 5 的 `BLPOP` 只能用整秒。
- 已挂断的会话仍计入 200 通上限。
- 凭证丢失无法找回。正文在 Redis 里是明文。
- 没有 TLS，没有按人隔离的呼叫名单。
- `appendfsync everysec` 可能丢掉约一秒的数据。验证用的是 `always`。

## 还要人来做的验收

需要后来的明确授权，才能动用户的 Linux 和 macOS。步骤：

1. 在 Linux 上安装 Python 3.12 和本仓库，Redis 使用不低于 5.0.14 的版本，并先看启动日志里的版本是不是三个已测版本之一。
2. 用 `appendfsync always` 或接受 `everysec` 的丢失窗口。Redis 只监听可信地址，并设置密码。
3. `HELLO_BIND` 设为局域网地址，`HELLO_ALLOWED_HOSTS` 设为客户端会写进 Host 头的 `主机:端口`。不要做端口映射到公网。
4. 用登记配置各登记一次，把两个 token 分别放进两台机器的 MCP 配置。一台可以是 Linux，另一台是 macOS。
5. 在真实的 Claude Code 里加载 `.mcp.json`，确认工具列表出现，再跑：心跳、呼叫、双向文字、一张真实 PNG、第二通会话隔离、挂断一通、离线留言、重启中心进程后用原 token 读到留言。
6. dsh 要先核对当前版本文档里的 profile 路径和 skill 路径，再把 `examples/mcp/dsh-entry.yaml` 放进去。跑通之前，配置只能标成未实测。图片还要确认那个模型的 attachment 是开的。
7. 只有这些在两台真实机器和真实主机上都做成了，才能说跨机器和主机验收通过。

## 还没定的问题

- 用户现有 Redis 如果低于 5.0.14，这一版会拒绝启动。要不要为那个具体版本再测，等看到 `redis-server --version`。
- dsh 插件条目要写进哪个文件，官方 README 没有在这次核对中给出。
- Claude Code 在用户那一版上，对局域网 `http://` 是否和文档示例一致。托管策略要求 `https`，那是另一条路径，本服务没有 TLS。
- 凭证丢失后要不要有人工恢复。现在没有。
- 已结束会话要不要释放名额。现在不释放。
